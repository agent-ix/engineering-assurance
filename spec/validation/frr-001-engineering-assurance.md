# Engineering Assurance proposed high process-risk supplier assessment

## Feature assessments

| Requirement | Failure mode | Detection |
|---|---|---|
| FR-004 | A producer result could be marked observed without its producer identity, or unavailable/not-computed/not-applicable states could be omitted or duplicated. | Run fixtures for observed, unavailable, not-computed, and not-applicable producers; compare the complete producer tuple and command outcome, then assert zero, duplicate, or conflicting states are rejected. |
| FR-005 | A resumed workflow could lose completed phases, reuse a run id for another decision boundary, or infer a terminal decision without a person. | Interrupt and resume each supported workflow, checking completed phases and next action; reuse the id with changed repository, workflow version, or boundary and assert refusal without state mutation; test explicit accept and reject choices. |
| FR-008 | If definitions, executions, results, and views have ambiguous owners, a consumer could treat a definition as evidence or gain an undeclared execution capability. | Validate that each semantic concept has one authoritative owner and link direction; inspect the contract for forbidden runner, shell execution, evidence persistence, and human-decision inference capabilities. |
| FR-009 | A projection could drop producer provenance or promote a failed/unavailable state to a successful observation. | Round-trip valid producer tuples and definition versions, then exercise each non-success state; verify projected values cite source record and field path and never claim a copied authority. |
| FR-015 | The Rust implementation could change canonical values or identity behavior when replacing the prior implementation. | Run focused fictional fixtures including integers beyond i64/u64 and compare canonical outputs and identities; inspect shipped source for copied portable-contract, persisted-evidence, or foreign-language executable logic. |
| FR-016 | The Rust onboarding or workflow evaluator could return a different inventory/status or accept a broken binding. | Run existing, absent, conflicting, malformed, unavailable, unjustified, and incomplete onboarding fixtures; break one binding and assert fail-closed status and agreement with the retained reference. |
| FR-017 | Rust evaluation or repository qualification could miss a host scenario or report a passing result when integration evidence is incomplete. | Execute every required host/scenario cell and compare success/failure outputs; submit integration-evidence fixtures with multiple failing conditions and assert all are returned with condition code, document, and line. |
| FR-019 | A producer request could run a different executable, exceed its resource/output bounds, or report completion without the retained output and provenance. | Run synthetic producers through the library boundary and assert one execution, exact executable/argv identity, bounded evidence, timing, provenance, retained artifact, and the declared timeout/output-limit errors. |
| FR-020 | A MeasurementPlan could accept an incomplete target objective or reject valid optional directions, changing which result is measured. | Validate plans for each supported direction with absent, numeric, and required bounds; assert target-without-bound and unknown fields fail, then compile the default-off measurement consumer. |
| FR-021 | An invalid comparator, estimator, threshold, or baseline could be accepted and change a measurement decision. | Exercise every comparator with threshold and baseline forms, including margin, unknown/missing comparator and malformed numeric boundaries; verify the schema rejects every invalid form and preserves the decision rule. |
| FR-022 | A claim-strength spelling could be changed, reordered, or owned by the wrong component, making the same claim mean something different to consumers. | Round-trip all four wire spellings through render/serialize/parse/deserialize; compare generated language listings with the ownership registry and assert the registry has one owner. |
| FR-023 | A supported claim could be accepted without an evidence reference or with duplicate/non-URI references. | Validate a supported claim with one valid ix:// reference, then remove it, empty the list, duplicate it, and use a non-ix URI; assert each unsupported shape is refused. |
| FR-024 | A gate MeasurementPlan could omit the protected apparatus or negative controls needed to identify changes that invalidate the measure. | Validate below-gate and gate plans with accepted apparatus paths, then test empty, repeated, non-file, and unlisted entries; exercise each negative-control kind and its required ground-truth fields. |
| FR-025 | A measurement could be promoted even when its typed checker result is failed, missing, or disallowed by the AssuranceProfile policy. | Submit typed checker fixtures for each policy mode and stage; assert only the permitted result advances and verify retired historical profiles remain readable while active profiles require the current schema version. |
| FR-026 | Invalid steering fields could change a MeasurementPlan objective through negative, non-finite, or out-of-range weight, half-life, or budget values. | Validate every combination of optional steering fields, including zero and large finite values; assert negative, non-finite, and invalid types fail and compile the minimal consumer. |
| FR-027 | Publishing could overwrite an existing artifact or leave a partial file after a failed write. | Publish exact bytes to an absent path, then retry against an existing path and run concurrent publishers; assert no replacement, no sidecars, and successful writes flush the sidecar and parent directory on Unix and Windows. |
| FR-029 | The installed producer-execute command could return a non-canonical result, conceal producer failure, or behave differently outside a Cargo checkout. | Run valid, invalid, timed-out, and bounded-output requests through the real binary; assert one canonical newline-terminated result, exact machine error and exit status, then invoke it with an empty environment from an unrelated directory. |
| FR-030 | An integrator package could serialize nondeterministically, accept malformed members, or fail for a consumer with only the package feature enabled. | Round-trip a package containing every fact kind and multiple adopter subjects; vary input order and compare bytes, feed malformed/unknown members and assert refusal, then compile the minimal default-off consumer. |
| FR-031 | A package could be published under the wrong candidate/attempt or overwritten, leaving an invalid or ambiguous evidence artifact. | Publish valid and invalid packages to candidate/attempt paths; assert valid bytes read back equal, invalid/missing-root cases write nothing, and distinct candidates/attempts coexist idempotently. |
| FR-032 | A declared change scope could be reported complete while a changed path is uncovered, or invalid revisions could start Git. | Compare exact-file and directory-prefix scopes against fixture change footprints; add an uncovered path and assert incomplete, then submit unreadable, malformed, invalid-scope, and option-like revisions and assert no Git process starts. |
| FR-033 | A non-boolean cross-profile comparison value could alter how measurements from different profiles are interpreted. | Validate true, false, and absent values; submit string, number, null, array, and object values and assert each is rejected. |
| FR-034 | An invalid paired-run relation or zero pair threshold could be used to compare non-comparable measurements. | Validate the absent relation, all three supported relations, and minimum_pairs boundaries; assert unknown relations, zero/negative/non-numeric thresholds, and relation-specific invalid fields are refused. |
| FR-035 | An incomplete or ambiguous population could be treated as the population measured, invalidating the resulting estimate. | Validate absent population declarations, distinct ids, and a reasoned exemption; assert empty/duplicate ids and invalid exemptions fail, including cases that declare both forms. |
| FR-036 | A bad or untrusted SSH signature could be reported as valid, or a valid commit/tag could be misclassified. | Use real repository fixtures with allowed and disallowed keys for signed commits and annotated tags; assert signed_valid, unsigned, signed_bad, and signed_untrusted outcomes, including required ssh-keygen failure cases. |
| FR-037 | A cryptographically valid signature could be mapped to the wrong person or meaning trailer, causing an approval to be attributed incorrectly. | Verify commit and tag fixtures against allowed-signers mappings and trailer blocks; alter principal, meaning, and trailer placement independently and assert mapping/status and returned trailers match the signed object. |
| FR-038 | A Syft request could identify the wrong executable/version or produce an SBOM that does not represent the requested source tree. | Run the declared Syft request over the fictional source fixture with stand-in and supported real executable; validate the request/result schema, component set, provenance, exit state, and version token. |

| FR-043 | The approval trail could omit, reorder, or hide revoked/invalid approvals and make the record history appear current when it is not. | Create valid approved and revoked tags plus missing, unreadable, and invalid receipt fixtures; compare the complete oldest-first trail, tag object ids, statuses, truncation, and unreadable entries. |
| FR-044 | An OSV-Scanner request could scan the wrong SBOM or omit a known advisory from the resulting evidence. | Run the declared request against retained npm, Rust, and container SBOM fixtures with the supplied local advisory database; assert known advisories and producer/version provenance in output. |
| FR-045 | Pandoc or Typst could be invoked with wrong arguments or produce a document that omits source headings/code. | Use stand-in converters to assert executable and argv, then convert the fixture with real pandoc and typst; inspect the DOCX document XML and PDF signature/content for the expected headings and code. |

## Rationale

This is a proposed supplier-side rating for IU-001. The named human assigned to review and accept it is Peter Krenesky. The record is unsigned and unaccepted pending his decision through the signed-commit workflow. No score or product-safety classification is assigned.

The listed features can affect whether engineering evidence is complete, correctly attributed, validated, private, or accepted by the stated policy. A failure could therefore make an engineering record appear verified, traceable, published, or approved when its supporting evidence does not justify that result. These proposed ratings are human judgments for review, not outputs calculated from code, test, coverage, or performance data.
