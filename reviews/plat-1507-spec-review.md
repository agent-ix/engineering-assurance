# Spec review of gitsign (Sigstore keyless) commit and tag verification (engineering-assurance PR 213)

## Summary

Ticket: PLAT-1507. Scope is `git diff origin/main...HEAD` only: new FR-040 and FR-036 amendments (Description out-of-scope paragraph, AC-10, Dependencies). FR-037 was read as context because FR-040 amends its signer model. Base checklist run; failure-domain and EARS lenses applied inline, following this repo's precedent (one spec-review document per spec PR). No AssuranceProfile in the repo requires an enforced spec-review run. `quire validate --scope . "spec/**/*.md"` exits 0 with two grammar warnings on FR-040 line 135.

gitsign is not installed here, so its behaviour was checked against its source at sigstore/gitsign main (latest release v0.18.0, 2026-10-20) and cosign's option parsing:

- `gitsign verify [commit]` (`cobra.MaximumNArgs(1)`, default HEAD) opens the repository at `.`, resolves a revision with go-git, reads only a commit object, takes `gpgsig` then `gpgsig-sha256`, and requires a PEM block of type `SIGNED MESSAGE`. git's own `x509_sigs` marker is `-----BEGIN SIGNED MESSAGE-----`, so FR-040's CMS detection matches both git and gitsign.
- `gitsign verify-tag <tag>` exists (added in #659, first released in v0.13.0). It takes `cobra.ExactArgs(1)`, a tag *name* resolved as `refs/tags/<name>`, and verifies the in-body signature block from the raw tag object.
- Both commands accept `--certificate-identity`, `--certificate-identity-regexp`, `--certificate-oidc-issuer` and `--certificate-oidc-issuer-regexp` (cosign `CertVerifyOptions`). cosign's `Identities()` requires one identity flag and one issuer flag and accepts `.*`; the wildcard probe is not rejected.
- `main` exits 2 when `config.Get()` fails and 1 for every error `Execute` returns. That covers repository open failure, unresolved revision, missing signature, non-CMS block, TUF or Fulcio-root load failure, CT-log key fetch failure, Rekor client or lookup failure, an invalid signature and an identity-policy mismatch. Exit status alone tells only "accepted" from "not accepted".
- `config.Get()` forks `git config --get-regexp .*` in the working directory, so repository-local `gitsign.*` keys apply. These include `gitsign.fulcioRoot`, which replaces the TUF-sourced Fulcio root (`fulcioroots.sourcesFromConfig`), plus `gitsign.rekor`, `gitsign.timestampCertChain`, `gitsign.enableSigstoreGo` and `gitsign.rekorMode`. Environment variables `SIGSTORE_ROOT_FILE`, `SIGSTORE_/GITSIGN_FULCIO_ROOT`, `*_REKOR_URL` and `*_TIMESTAMP_CERT_CHAIN` override them.
- Verification is not hermetic: the Fulcio root and CT-log keys come from a TUF client (embedded or cached root, with a network update when it has expired), and Rekor is consulted, online for "online"-mode signatures.

Checked and found consistent:

- Ticket design decisions (read as data): delegation with no own crypto (Behavior, CON-2, AC-14); an optional identity and a named reason when it is absent (`gitsign_identity_missing`, AC-5); `signature_kind` plus the accepted identity and issuer (Outputs, AC-1); no person from author or email (Behavior); stand-in-only ACs labelled (Stand-in note); X.509 amended for gitsign only (FR-036 Description and AC-10, but see FND-008); FR-036 hardening reused (prefix headers, no message text, pinned program, separate arguments, bounds).
- Hardening parity: headers matched as prefixes; classification from exit statuses, not message text; program name pinned; arguments passed without a shell, with the revision after `--`, which cobra treats as positional; request-field bounds (256 bytes, no control character, no leading `-`, unknown members rejected, AC-11); 60 s and 8 MiB per invocation. The gaps are in configuration and environment isolation (FND-003, FND-004).
- Mapping model: `mapped` is reported only after gitsign accepted the exact identity and issuer, and `principal` is the caller's declaration. That is the same trust as the caller-supplied allowed-signers file of FR-036/FR-037. The caller cannot get `mapped` without gitsign's acceptance, provided gitsign's trust roots are not repository-controlled (FND-003), and FR-037 has not yet been amended to allow it (FND-006).
- The Stand-in note says plainly that no criterion shows a real Sigstore signature verifies.
- Public-repo hygiene: no roadmap, delivery order, research content or private paths; no SHA, pin, digest or tracking ceremony added.

## Verdict

The design follows FR-036: gitsign decides, a closed classification is reported, and no person is inferred. The CMS marker, the gitsign storage locations, the flag names and the acceptance of `.*` regexps all match real gitsign and git. The request bounds and the stand-in disclosure are good, and public-repo hygiene is clean.

It is not mergeable. Measured against gitsign's source, the exit-status classification cannot tell a bad signature from an infrastructure failure (FND-001). The invocation count contradicts AC-3 (FND-002). gitsign's trust root is controllable by the repository under verification (FND-003). FR-036 and FR-037 keep normative text that FR-040 violates (FND-005, FND-006). FND-001 through FND-009 should be fixed; the two lows are small edits.

## Dispositions

Round 1, against fix commit aca4227. The new claims were re-checked against gitsign v0.18.0 source and against git 2.34.1 in a throwaway repository (deleted afterwards). Under `GIT_CONFIG_NOSYSTEM=1 GIT_CONFIG_GLOBAL=/dev/null`, a repository whose `.git/config` has `include.path = ../evil.cfg`, where that file sets `gitsign.fulcioRoot`, behaves as follows:

- `git config --local --get-regexp '^gitsign\.'` exits 1 with no output, because `--local` turns includes off.
- `git config --get-regexp '.*'`, which is what gitsign runs, prints `gitsign.fulcioroot /tmp/evil.pem`.
- `git config --local --includes --get-regexp '^gitsign\.'` exits 0.

The same holds for a key in `config.worktree` with `extensions.worktreeConfig` set: `--local` misses it and the unscoped read returns it.

The rest of the fix checks out:

- **Environment:** `PATH`, `HOME`, `GIT_CONFIG_NOSYSTEM` and `GIT_CONFIG_GLOBAL` are sufficient. sigstore's `tuf.NewFromEnv` defaults its cache under `$HOME/.sigstore` and forces a remote update, so the network claim and the third clause of FR-040-AC-15 hold. With `GIT_CONFIG_COUNT` and `GIT_CONFIG_PARAMETERS` not passed, system and global config scrubbed, and `SIGSTORE_*`, `GITSIGN_*` and `TUF_ROOT` withheld, the only remaining channel is repository config, which is FND-003.
- **Four-run procedure:** sound, and it matches cosign's `Identities()`.
- **`signer.source`:** consistent with the amended FR-037 Outputs, Behavior and CON-1.
- **`verify-tag` name derivation:** matches gitsign's `refs/tags/<name>` lookup.

The design accepts one residual: a transient network failure between probes can still turn a valid signature into `signed_untrusted`, or pick the wrong `mismatch` value. That errs on the safe side and is not recorded as a finding.
