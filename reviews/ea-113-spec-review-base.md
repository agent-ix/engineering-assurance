# Spec review (base) of EA PR 305

## Summary

Ticket: EA-113 (re-authentication at signing, baseline tier). Review set: subset (base, ears-conformance, integrity); the EARS and integrity lenses have their own SpecReview files. No AssuranceProfile in the repo requires an enforced spec-review run, so this is a direct review. `quire validate --scope .` on FR-042 and FR-084..087 (quire 0.52.0, engine 0.62.2) exits 0; the only output is the existing `DuplicateModuleName` notice. No cargo, tests or make ci were run (spec-only).

What was measured against the dependency FR-084 relies on (OpenSSH): the local `ssh-keygen` is OpenSSH 8.9p1, and its man page was checked along with openssh-portable master `ssh-keygen.c`, `sshsig.c` and `ssh-ed25519-sk.c`. `-Y verify` accepts only the `-O` options `hashalg=`, `verify-time=` and `print-pubkey`, and it rejects any other option with `Invalid option` (non-zero exit). The allowed-signers grammar (`sshsigopt_parse`) knows only `cert-authority`, `namespaces`, `valid-after` and `valid-before`; any other option fails the line as `unknown key option`. `verify-required` and `no-touch-required` are key-generation options and `authorized_keys` (sshd) options, not `-Y verify` or allowed-signers options. `sshkey_verify` for `-sk` keys copies the signature flags into `sig_details` and enforces neither user presence nor user verification. `ssh-keygen -Y verify` prints the flags only at debug level 2 (`signature details: counter = %u, flags = 0x%02x`, so `-vv`, on stderr).

Ids: FR-084, FR-085, FR-086 and FR-087 appear in no earlier commit on any ref, and no other open EA PR uses them (#304 adds FR-081..083). Overlap: `git merge-tree` of origin/main (with merged #303) and this head has no conflict. #303's `trust` members and `signed_at`/`trusted_at` sit beside the new `gesture` members, with no name collision. #304 edits FR-043's status set (`missing_tag`, `invalid_receipt`, `accepted`), and FR-086's "status other than `approved` carries no `gesture`" already covers those. No paywalled standard is quoted; 21 CFR 11.200(a) is cited by section only. spec/tests.md is untouched by design (the matrix is generated).

## Verdict

FAIL for round 1 on FND-001 (high). FR-085 and FR-087 are sound in intent, and so is the honest treatment of `ssh-add -c` and interactive gitsign. Those modes leave no trace in the signature, so `evidenced` `none` with a separate declared value states only what can be shown and does not overclaim; that meets the owner's "report the gesture mode" intent, provided FR-087 says plainly that the declared value is the caller's claim, which it does. `gitsign` reported always `none` is correct: a Fulcio certificate shows a login happened, not a per-signature gesture, and gitsign can reuse a cached certificate. Nothing assigns a score, class or acceptability, except that FND-003's `declared_status` labels lean that way.

The 300 second interactive timeout belongs in the spec. It is a bound the caller observes, it is the counterpart of FR-042's 60 seconds, and FR-085-AC-7 tests it; it needs no rationale beyond that. The FR-042 edit must not contradict it; see the integrity lens.

FR-084, however, is built on `ssh-keygen` behaviour that was measured not to exist. Its main claim, that touch was enforced, is false for a `no-touch-required` key. Its other two values cannot be reached, and its stand-in ACs would certify the fiction. FND-001 and FND-002 should be resolved together by naming one real ssh-keygen output that carries the key type and flags.
