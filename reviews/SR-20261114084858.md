## Summary

Reviewed EA-123 PR #274's private Git adapter, sink integration, fixtures, source audit, and changed Test Case rows. The adapter has a reachable symlink escape, reads unrelated refs during clone, and has outcome-error and test-evidence gaps; the required all-target Clippy command also fails.

## Verdict

**FAIL** — two high-severity findings include a remote-controlled filesystem write outside the temporary checkout and duplicated validation logic; four additional medium findings remain.

## Scope

The following changed behavior was checked against its acceptance criteria. Excerpts are verbatim.

- FR-054-AC-7 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): For a fixture public source repository with the Git private-store destination configured, publishing its record creates the private-form file at the specified path on `refs/heads/engineering-assurance-private-records`; no private-form bytes or source-repository notes are written to the public source repository.
- FR-054-AC-8 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): A private-store publish creates the matching `public.json` beside `private.json`; a public-log publish does not create `public.json` in the private Git store; both non-`none` paths persist the selected sink's exact final outcome in `outcome.json`.
- FR-054-AC-9 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): Reapplying a Git file write after a non-fast-forward update with the same bytes succeeds without changing stored bytes; different bytes for the same record path fail with `private_store_write_failed` and preserve the original.
- FR-054-AC-10 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): Two concurrent writes with different record IDs both remain readable after retrying a non-fast-forward push; after five failed push attempts and a refreshed target ref that lacks the record file, the write fails with `private_store_write_failed` without force-pushing or deleting a record.
- FR-054-AC-11 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): A record for a source repository whose owner or repository component is `.` or `..` is stored under the lowercase-hex path component for that exact UTF-8 value, and the resulting path contains no `.` or `..` directory component.
- FR-054-AC-12 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): A stored approval private form is UTF-8 RFC 8785 canonical JSON; canonicalizing its nested statement object reproduces byte-for-byte the statement bytes passed to the signer, and decoding it preserves the exact signature-bundle string.
- FR-054-AC-13 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): After a public-log success, private-store success, or sink refusal, `outcome.json` contains the canonical outcome statement, exact Sigstore bundle and specified record ID, sink and outcome; a failed outcome write yields `refused` with `private_store_outcome_write_failed`. The `none` sink creates no private-store files.
- FR-054-AC-14 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): Writing the same final sink and outcome again for a record ID succeeds without changing the signed marker; attempting to replace it with a different sink or outcome fails with `private_store_outcome_write_failed` and preserves the original marker.
- FR-054-AC-15 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): Replaying a record with an identical private form and a valid signed `published` outcome returns `published` without invoking its sink; replaying one with a valid signed `refused` outcome returns `refused` with `private_store_record_previously_refused` without invoking its sink.
- FR-054-AC-16 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): A prior private form without a valid signed terminal outcome, private bytes conflicting with the proposed form, or a public-form file inconsistent with the verified stored sink/outcome fails closed before the selected sink is invoked. A fresh record ID is required for a new publish attempt.
- FR-054-AC-17 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): An outcome marker with a changed outcome field or signature bundle, or a valid signature from an identity other than the configured `record_publisher`, makes the private-store lookup fail with `input_unreadable`; no public-log call is made to sign or verify the marker.
- FR-054-AC-18 (`spec/functional/FR-054-record-sink-interface-and-implementations.md`): When two same-ID preparations race, at most one returns `NewRecord`; the other observes the winner and returns its valid terminal outcome or fails closed if the marker is incomplete, and the selected sink is invoked at most once.
- FR-055-AC-8 (`spec/functional/FR-055-per-repo-sink-configuration-and-visibility-default.md`): A `private_store.destination` that is not exactly `owner/name` or whose canonical ASCII-lowercase owner/name equals the publishing repository's canonical identity is refused with `sink_config_invalid` before a private form is written.
- FR-055-AC-9 (`spec/functional/FR-055-per-repo-sink-configuration-and-visibility-default.md`): A valid destination is read and written only at `refs/heads/engineering-assurance-private-records`; a sink configuration that attempts to supply a different ref is refused with `sink_config_invalid`.
- FR-055-AC-10 (`spec/functional/FR-055-per-repo-sink-configuration-and-visibility-default.md`): A destination that differs from the publishing repository only by ASCII letter case is refused with `sink_config_invalid` before any private form is written.
- FR-056-AC-11 (`spec/functional/FR-056-public-and-private-record-split.md`): An approval private form contains exactly the full statement object and the exact signature-bundle string returned by the signer; an unknown member inside the `statement` envelope is rejected.
- FR-058-AC-10 (`spec/functional/FR-058-approval-statement-and-predicate.md`): The bytes passed to the statement signer equal the RFC 8785 canonical JSON encoding of the full statement object; the private form stores that statement object and the exact signature-bundle string returned by the signer.
- FR-064-AC-21 (`spec/functional/FR-064-verify-approval-statement-with-workflow-identity-policy.md`): A Git private-store lookup reads the configured destination's fixed ref and returns every statement for the exact repository, merged pull request and merged commit, in ascending record-ID order; a statement with a different repository, pull request or commit is omitted.
- FR-064-AC-22 (`spec/functional/FR-064-verify-approval-statement-with-workflow-identity-policy.md`): A malformed private-form file, missing or malformed signed outcome, invalid outcome signature, untrusted outcome signer, or failed Git tree/blob read yields `unverifiable` with reason `input_unreadable` and returns no partial statement set; a readable store with no matching record yields `statements_not_retained`.
- FR-064-AC-23 (`spec/functional/FR-064-verify-approval-statement-with-workflow-identity-policy.md`): After the Git private-store round trip, the exact RFC 8785 approval-statement bytes, signature-bundle string, and verified final publish outcome are returned unchanged; the verifier accepts a published fixture statement and rejects a one-byte change.
- FR-064-AC-24 (`spec/functional/FR-064-verify-approval-statement-with-workflow-identity-policy.md`): Changing a well-formed stored outcome field or its bundle after signing makes the private-store read `unverifiable` with reason `input_unreadable`, even when the changed outcome remains structurally valid.

The symlink finding is reproducible: checking out a branch containing `records/61636d65` as a symlink makes `create_dir_all` and `fs::write` follow it outside the clone. The probe confirmed the write landed in a sibling directory. Existing `src/record_sink/config.rs::valid_repository` already implements the same grammar as the two new copies; this was checked before reporting duplication. A local bare-remote probe also confirmed `git clone --no-checkout` fetched both `main` and the private-store branch.

The changed Rust files individually pass `rustfmt --check`. Workspace `cargo fmt --all -- --check` fails on the same pre-existing generated files on `origin/main`, so that is not attributed to this PR. `cargo deny check` passed using a writable temporary Cargo home (with only existing unmatched-allowance warnings). Focused private-store (3), record-sink (34), and source-audit (18) tests passed. `cargo clippy --workspace --all-targets --all-features -- -D warnings` failed with 8 errors in the new test module: two `too_many_lines` findings and six `needless_borrow` findings.

Bindings examined: `tc_991_approval_lookup_reads_exact_statement_bytes_bundle_and_signed_outcome` cites FR-064-AC-23; the trace points to the right criterion, but the assertion does not establish that the approval bundle was valid before storage.
