## Verdict

**FAIL** - two medium findings with a wrong result on a reachable history: records already in the previous release are listed again when the previous baseline joins the baseline's first-parent history only through a merge (FND-001), and the previous tag is resolved with rev-parse ref guessing rather than only as `refs/tags/<name>` (FND-002).

Checked and clean: first-parent semantics on the main path (`log --first-parent --root --no-renames --diff-merges=first-parent --diff-filter=A`; a merge is judged against its first parent; the root against the empty tree); the previous baseline is the single parent of the release commit the tag peels to; earliest add wins in first-parent order, whatever the dates; `^boundary` correctly bounds the walk at the previous baseline; deletion before the baseline is filtered by `ls-tree` at the baseline. Hardening matches release-verify: the shared `run_git` sets GIT_NO_REPLACE_OBJECTS, GIT_GRAFT_FILE, GIT_CONFIG_NOSYSTEM/GLOBAL, GIT_OPTIONAL_LOCKS=0, the 60 s timeout and the 8 MiB output cap; `--literal-pathspecs` on `log` and `ls-tree`; `--end-of-options` on rev-parse and rev-list; every git failure or unparsable token is an error, never a partial list. Path grammar matches FR-052 (record_id 1..256 bytes, not `.`/`..`, revision without sign, leading zero or fraction, `.json` only, deeper paths ignored); ordering is bytewise record_id, numeric revision, bytewise commit; one entry per (record_id, revision). No record file is opened, parsed or hashed (FR-052-AC-14 inspected: only `ls-tree`, `log --raw`, `rev-list`, `rev-parse`, `merge-base`). No hashing, digest or crypto code. Result members and order match quoin FR-168 Inputs; `baseline_commit` is echoed byte for byte. Registration: subcommand, capability constant, dispatch, `release-history` feature in `full`, lib.rs feature table row, README row and TC-098 (18 cases) are all present and consistent. TC-500..514 rows are tagged to the ACs they assert. Ticket discrepancy (data): the EA-103 AC 'the release record names the previous release tag' conflicts with merged FR-047/FR-052, which take the previous tag as a request input; the PR follows the spec, as the lead's note asks.

## Findings

| ID | Severity | Summary | Refs |
| --- | --- | --- | --- |
| FND-001 | medium | Previous baseline reachable only through a merge (release cut on a release branch, merged back): commits_in_range invents a range rule (first-parent commits not among the previous baseline's ancestors) that FR-052 does not state, and the merge commit, judged against its first parent, re-lists every record the previous baseline already had. Reproduced: record inprev added at the previous baseline P on branch rel, rel merged into main at M; the result lists inprev at M although it was in release v1. FR-052 says to walk first-parent history back to the previous baseline, which does not exist on this chain, so the spec is silent and the code picks a wrong answer. No test covers the branch. Fix: get a spec ruling (refuse, e.g. extend release_history_previous_not_ancestor to 'not on the first-parent history', or exclude paths present at the previous baseline) and test it. | src/release_history_host.rs:247-266 |
| FND-002 | medium | previous_release resolves the tag with rev-parse --verify refs/tags/<name>, which applies ref guessing: with no tag v2, a branch refs/heads/refs/tags/v2 is accepted as tag v2; a tag named refs/tags/v3 (refs/tags/refs/tags/v3) is accepted as v3 (both reproduced, exit 0 with previous_release set). FR-052: 'SHALL resolve previous_release_tag only as refs/tags/<name>' and report release_history_previous_tag_unknown otherwise. signature_verify_host already guards this with rev-parse --symbolic-full-name. Resolve exactly (e.g. git show-ref --verify refs/tags/<name>, or check --symbolic-full-name equals refs/tags/<name>) and add the case to TC-512. | src/release_history_host.rs:182-184 |
| FND-003 | low | A request with no previous_release_tag member is accepted as a first release (serde Option defaults missing to None) and lists every record at the baseline. FR-052 Inputs names previous_release_tag as a member that is a tag name or null; omission is not null. Unknown members are refused, so only outright omission slips through. Refuse a missing member with release_history_request_invalid (serde_with double-option or a Value presence check) and test it. | src/release_history_host.rs:32 |
| FND-004 | low | Refusals beyond FR-052's grammar: records_dir './records', 'a//b', 'a/.' and control characters are refused although FR-052 Inputs allows them (non-empty, no '..', no leading '/', no glob); tag names containing '{' or '}' are refused although they are valid git ref names. A repository with more than about 200k first-parent commits fails with release_history_git_failed even for a one-commit range. Use rev-list --first-parent baseline ^previous (or merge-base --is-ancestor plus a first-parent membership check) and drop Range.commits. | src/release_history_host.rs:231-245 |
| FND-007 | low | Grammar-valid record paths are silently dropped: a revision above u64::MAX (FR-052 and quoin FR-063 set no upper bound) and a record_id that is not UTF-8. Both are vanishingly rare; either state the bound in FR-052 or refuse with an error rather than omitting a record from the version history without a trace. | src/release_history.rs:62-74 |
